# 具体实施参数与预期效果

本文把前面方案收敛成一套可执行的首版参数。这里的“预期效果”是容量设计目标和验收门槛，不是未经压测的线上承诺；最终值必须用隔离环境压测校准。

## 1. 先明确优化对象

你的计费表不是每个模型调用一行，而是：

```text
固定5分钟窗口 + 站点 + 用户 + 模型 + API Key = 一行
```

同一窗口内：

```text
第一次出现 → INSERT
后续批次 → 对同一行做 Token 增量 UPDATE
```

因此需要同时优化两类压力：

| 压力 | 由什么决定 | 对应优化 |
|---|---|---|
| 历史数据增长 | 每窗口唯一键 K × 每天288个窗口 | 日分区、归档、未来分库 |
| 在线写入压力 | 刷新频率 × 每批涉及的唯一键 | 本地聚合、批量 Upsert、Checkpoint |

## 2. 首版推荐参数

| 参数 | 首版建议 | 调整依据 |
|---|---:|---|
| Kafka 原始 Topic | 先保持4分区压测 | 只有单分区不足才扩 |
| 第一次扩容 | 8分区 + 4个Pod | 每Pod约2个分区 |
| 第二次扩容 | 12/16分区 + 6/8个Pod | 依据 Lag 和故障余量 |
| 聚合刷新间隔 | 10～15秒 | 与 DB P99、内存和恢复量共同校准 |
| 单分区批次上限 | 以 1～5 秒输入量为上限 | 避免长事务和大批次重放 |
| 窗口迟到宽限 | 2～3分钟 | 保证窗口结束后5分钟内上报 |
| 窗口控制粒度 | `window_start + virtual_bucket` | 支持多Pod并行固化 |
| 虚拟桶数 | 256 | 先逻辑分桶，不立即分库 |
| Outbox领取 | `SKIP LOCKED` 或租约 | 多Pod安全竞争 |
| 话单批量大小 | 500～2,000条压测 | 以 Kafka 和元数据 P99 决定 |
| 话单构建Worker | 4/8/16档压测 | 目标达到至少1,700条/秒 |
| 聚合表物理分区 | 按日 | 5分钟是业务粒度，不是物理分区粒度 |

## 3. 每项修改的具体动作和收益

### 3.1 分区级本地聚合

改什么：

```text
Kafka Poll
→ 按分区进入有界队列
→ 按 window_start + billing_key 聚合
→ 10～15秒或阈值触发批量刷新
```

不改什么：仍然是同一个五分钟固定窗口，仍然是同一聚合行累加，不改业务计费粒度。

预期收益：

- 数据库写入从“接近每条消息一次”降为“每批每个活跃键一次”；
- 50k QPS 时，数据库不会直接承受 50k 次/秒的更新；
- Poll 不被数据库慢请求阻塞；
- 单分区可独立 Pause/Resume。

效果如何验证：

```text
DB Upsert行数/原始消息数
DB事务数/原始消息数
批量刷新P95/P99
```

首版目标：在窗口唯一键为 1万～10万时，数据库更新量应明显低于原始 Kafka 消息量，且刷新事务 P99 不超过一个刷新周期。

主要风险：刷新间隔越长，内存和故障重放量越大。通过 5、10、15、30 秒四档压测选值。

### 3.2 数据库原子 Upsert

改什么：

```sql
input_tokens  = current.input_tokens  + delta.input_tokens
output_tokens = current.output_tokens + delta.output_tokens
request_count = current.request_count + delta.request_count
```

禁止在 Go 中读取旧值后再计算新值。

预期收益：多个 Pod 或 Rebalance 重叠时不会出现丢失更新。

主要风险：热点聚合键可能出现行锁等待；通过 Kafka 稳定分区键、较小批次和死锁退避降低风险。

验收：并发注入同一聚合键，最终 Token 必须等于所有增量之和。

### 3.3 分区 Checkpoint

改什么：为每个 Kafka 分区保存 `next_offset`，在同一 DB 事务内完成：

```text
锁定Checkpoint
→ 校验批次Offset连续
→ 原子Upsert增量
→ 推进Checkpoint
→ 提交事务
→ 再提交Kafka Offset
```

预期收益：

- DB 已提交、Kafka Offset 未提交时重放不会重复累计；
- Pod 强杀和 Rebalance 后可以从数据库进度恢复；
- 可以发现 Offset 缺口和部分重叠。

主要风险：Checkpoint 行是每个分区的串行点；因此必须按分区拆批、控制事务时长，不能把远程查询放进事务。

验收：在“DB提交后、Offset提交前”强杀 Pod，恢复后 Token 不增加。

### 3.4 窗口桶状态机

改什么：将窗口固化从每个 Pod 的定时任务改为数据库条件领取：

```text
OPEN → WAITING → FINALIZING → FINALIZED
```

控制键：

```text
site_id + window_start + virtual_bucket
```

预期收益：

- 多个 Pod 同时运行定时任务也只会有一个获得固化权；
- 10万聚合键可按桶并行生成话单；
- Pod 崩溃后租约到期可接管。

主要风险：累计和固化并发时可能少计。所有写路径必须采用统一锁顺序；晚到数据进入修正路径，不能静默覆盖已发送话单。

### 3.5 Outbox 话单发送

改什么：窗口固化事务中生成确定性 `bill_id` 并插入 `billing_outbox`；发送 Worker 使用租约或 `SKIP LOCKED` 批量领取。

预期收益：

- 上报任务不再扫描历史聚合表；
- 失败任务不会因窗口变旧而漏掉；
- 话单 Worker 可以独立扩容；
- Kafka 或元数据服务短时故障不会阻塞原始消费。

目标吞吐：

```text
10万话单 / 3分钟 ≈ 556条/秒
建议压测目标 ≥ 1,700条/秒
```

主要风险：Kafka 已发送、数据库未标记 `SENT` 时会重发。必须由结算系统按 `bill_id` 幂等；Producer 幂等不能替代业务幂等。

### 3.6 元数据批量缓存

改什么：原始消费阶段只保存用户、模型、API Key ID；话单阶段收集一批中的唯一 ID，批量查询并使用本地缓存。

预期收益：

```text
查询量从随原始QPS增长
降为随唯一元数据ID数量增长
```

主要风险：影响计费的元数据若只使用 TTL，重放时可能生成不同费用。价格、归属和模型计费规则需要版本化。

### 3.7 聚合表日分区

改什么：业务仍按5分钟聚合，数据库按 `window_start` 的日期分区。

预期收益：

- 最近窗口查询具备分区裁剪；
- 归档和删除按日执行；
- 单个索引和维护任务规模受控。

主要风险：日分区不会提高单库总写入能力；单库达到资源边界后仍需按虚拟桶分库。

## 4. 预期效果模型

以下是设计目标，不是现网实测结果：

| 指标 | 当前问题形态 | 优化后的目标 |
|---|---|---|
| 原始消费 | 4分区、4 Pod、目标吞吐未知 | 4分区先压测，必要时渐进到8/12/16 |
| DB写入 | 批次内重复更新可能过多 | 本地合并后批量 Upsert，按刷新周期受控 |
| 多Pod一致性 | Redis + Kafka Offset，存在故障窗口 | DB Checkpoint + 原子 Upsert |
| Rebalance | 可能重复重放 | 从 DB Checkpoint Seek，重放不重复累计 |
| 窗口固化 | 多Pod定时任务可能重复 | 窗口桶条件领取/租约 |
| 话单失败 | 依赖最近时间扫描 | Outbox可重试、可审计、可接管 |
| 元数据查询 | 可能在话单批次形成尖峰 | 批量去重、本地缓存、提前预热 |
| 历史表维护 | 数据持续增长 | 每日分区、分区归档 |
| 目标容量 | 5k → 50k QPS | 50k持续 + 75k突发压测通过 |
| 上报时延 | 依赖定时任务窗口 | 窗口结束后5分钟内完成 |

## 5. 建议的验收门槛

必须同时满足：

- 50k QPS持续运行时 Consumer Lag 不持续增长；
- 75k QPS突发后，追平速度高于积压产生速度；
- 单 Pod 强杀后其他 Pod 继续消费；
- 10万聚合键窗口在窗口结束后5分钟内完成话单上报；
- 同一 Offset 重放后 Token 不增加；
- 数据库并发累计无丢失更新；
- 两个 Pod 同时关闭同一窗口桶只生成一份正式 Outbox；
- Kafka 重发同一 `bill_id` 时下游只结算一次；
- 元数据查询量不随原始 50k QPS线性增长；
- MySQL 与 PostgreSQL 在相同故障测试下结果一致。

## 6. 首先应该做什么

不要先扩 Kafka 或分库。首轮执行顺序：

1. 记录当前 4 分区、4 Pod 的基线；
2. 测量每批消息数、每批聚合键数、DB Upsert 行数和事务 P99；
3. 加入分区级 Checkpoint 和原子 Upsert；
4. 用 5/10/15 秒刷新周期做压测；
5. 增加窗口桶状态机和 Outbox；
6. 在优化后的消费者上重新评估4分区是否足够；
7. 只有单分区吞吐不足时，再创建8分区 Topic做双写验证。

最终判断依据是压测指标，不是“50k QPS所以必须24分区”或“聚合键变多所以必须立刻分库”。
