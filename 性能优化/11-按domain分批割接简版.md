# 按 domain_id 分批割接（简版）

## 目标

允许 Kafka 积压和话单延迟，但不允许漏计、重复计费或发送未校验话单；旧粒度话单从窗口结束起最迟 2 小时上报。

## 一条原则

**同一个 domain_id + 五分钟窗口，旧表只能有一个写入者。**

## 三种状态

| 状态 | 旧表写入 | API Key 明细表 | 上报 |
|---|---|---|---|
| `LEGACY` | Kafka 直接写 | 否 | 正常 |
| `DUAL` | Kafka 直接写 | Kafka 写入 | 暂停，先校验 |
| `DETAIL` | 明细汇总写 | Kafka 写入 | 校验通过后 |

`DUAL` 状态禁止明细汇总任务写旧表；切到 `DETAIL` 后禁止 Kafka 直接写旧表。

## 按 domain_id 的切换步骤

1. 提前建明细表、唯一索引和窗口控制表，所有 domain 保持 `LEGACY`。
2. 选择一个完整五分钟边界 `T`，例如 `12:00`，只将一个低流量 domain 切到 `DUAL`。
3. 双写 1～2 个完整窗口，暂停该 domain 的话单上报。
4. 对比旧表与明细表汇总结果：消息数、聚合键数和每个 factor 的总和。
5. 校验通过后，在下一个五分钟边界将该 domain 切到 `DETAIL`。
6. `DETAIL` 窗口关闭且满足允许迟到水位后，从明细表**覆盖式**汇总旧表。
7. 校验通过后将窗口标记 `READY`，再生成并发送两类话单。
8. 观察至少一个 2 小时周期，再切换下一个 domain。

## 窗口写入归属

| 窗口状态 | Kafka 直接写旧表 | Kafka 写明细表 | 明细汇总写旧表 |
|---|---:|---:|---:|
| `LEGACY` | 是 | 否 | 否 |
| `DUAL` | 是 | 是 | 否 |
| `DETAIL` | 否 | 是 | 是 |
| `VALIDATING` | 否 | 视重算策略 | 否 |
| `READY/REPORTED` | 否 | 否 | 否 |

明细汇总写旧表时使用“结果覆盖”，不能使用 `old + summary`，避免双写期间重复累计。

## 校验清单

对每个 `domain_id + window_start` 校验：

- 旧表 `factor1/factor2/...` = 明细表按 API Key `SUM` 的结果；
- 去重后的 `request_id` 数量和 factor 总量一致；
- API Key 聚合键无缺失、无串账；
- 话单总量与旧表/明细汇总一致；
- Kafka Lag、数据库错误、重试数均在阈值内。

只有 `validation_status=PASSED` 的窗口才能进入 `READY`。

## 失败与回滚

- 校验失败：保持 `DUAL`，暂停该窗口上报，重算后再校验。
- 明细路径异常：将该 domain 切回 `LEGACY`，不删除新表、不回退 Offset。
- 旧表汇总失败：保留窗口为 `VALIDATING`，重试覆盖写入。
- 话单发送失败：使用同一 `bill_id` 重试，避免重复结算。

## 时间约束

需要先确认有效消息的最大迟到时间。只有在“所有有效事件都能在窗口结束后 2 小时内到达”的前提下，才能同时保证完全准确和 2 小时内上报；否则必须选择延迟上报或设置补发/冲正机制。
